# 阶梯 0:地基(三个问题撑起整个项目)

## 完整讲解

### 0.1 两个程序怎么隔着网络说话?

你的浏览器和 NexusChat 的网关是两个程序,跑在(可能)不同的机器上。它们说话靠的是 **socket(套接字)**。

把网络世界想成一座巨大的写字楼:
- **IP 地址** = 楼里某家公司的门牌(找到那台机器)
- **端口** = 这家公司里具体某个工位(找到那台机器上的某个程序)。NexusChat 网关坐在 8080 工位,MySQL 坐在 3306,Redis 坐在 6379——回头看 `deploy/docker-compose.yml`,全对得上
- **socket** = 拨通后的一条电话线:你拨"IP:端口",对方接了,这条线就建立了,双方往线里写字节、从线里读字节

绝大多数通话用 **TCP** 协议建立:拨号时双方先确认"你能听到我吗/我能听到你"(这就是著名的三次握手,细节后面看小林,现在知道"先确认再说话"就够),之后这条线保证字节**不丢、不乱序**地送达。

**一句话:网络通信 = 拨通一条"IP:端口"的电话线,然后双方读写字节。**

### 0.2 程序等一个慢操作时,在干什么?

答案令人发指:**什么也不干,就是干等。** 这叫**同步阻塞**。

```go
result := db.Query("SELECT ...")   // 这一行要 10 毫秒
fmt.Println(result)                // 在上一行返回前,这里永远到不了
```

就像你在奶茶店点单,店员说"等 3 分钟",你就站在柜台前盯着,什么也不能干——这是**同步**。
如果店员给你个取餐号,你回座位刷手机,好了叫你——这是**异步**。

10 毫秒听起来很短,但灾难在于**并发**:1000 个用户同时让你的程序做 10ms 的事,
而你的程序一次只能干等一件,队尾那个人要等 10 秒。怎么办?雇更多"店员"。
Go 语言的店员叫 **goroutine**——超级便宜的轻量线程,雇几万个都行。
NexusChat 网关就是每来一个 WebSocket 连接,雇一个 goroutine 专门伺候它。

但 goroutine 再多也救不了所有场面(比如它们全卡在等同一个数据库),
这就是阶梯 2(Kafka)要解决的问题。先记住这句:**同步 = 干等;并发多了,干等会堆成雪崩。**

### 0.3 为什么内存快、磁盘慢、网络更慢?

记住三个数量级(不用精确,记倍数关系):

| 操作 | 耗时 | 等比例放大成人类时间 |
|---|---|---|
| 读内存 | ~100 纳秒 | 伸手拿桌上的笔:1 秒 |
| 读 SSD 磁盘 | ~0.1 毫秒 | 下楼取个快递:15 分钟 |
| 同机房网络往返 | ~0.5 毫秒 | 出门跑趟超市:1 小时 |
| 一次 MySQL 查询(磁盘+解析+网络) | ~1–10 毫秒 | 跨城办个事:一两天 |

**为什么这是整个项目的总钥匙:** NexusChat 里所有"高级设计",动机全是这张表——
- 凡是**慢的事**(写 MySQL),想办法挪出主路、让它慢慢办 → 这就是 Kafka(阶梯 2)
- 凡是**常用的数据**(谁在线、最新 100 条消息),搬到快的地方 → 这就是 Redis(阶梯 3)

后面每次看不懂"为什么这么设计",回到这张表,答案多半在里面。

## 实验(10 分钟)

不用写代码,感受数量级:
```bash
ping baidu.com        # 看一次网络往返多少毫秒(跨城网络)
docker compose exec redis redis-cli --latency   # 看 Redis 一次操作多少毫秒(内存,按 Ctrl+C 停)
```
对比两个数字,差几十倍——这就是"把数据放内存"的全部理由。

## 自查题

1. 浏览器连接 NexusChat 网关,完整的"地址"是什么?由哪两部分组成?
2. 1000 个请求同时到达,每个要做一次 10ms 的数据库写,单个同步处理的程序,最后一个请求等多久?
3. 同样一份"用户是否在线"的数据,放 MySQL 和放 Redis,单次查询大约差多少倍?

## 参考答案(先自己答!)

1. `IP:端口`,本机实验里是 `localhost:8080`。IP 找到机器,端口找到机器上的网关进程。两者合起来才能"拨通电话"。
2. 约 10 秒(1000 × 10ms 排队)。这就是为什么需要并发(多个 goroutine)+ 异步(不让任何人干等慢操作)。
3. 约 10–100 倍(Redis 内存 ~0.1ms vs MySQL 磁盘+解析 ~1–10ms)。而且 Redis 不用解析 SQL、不走 B+ 树,高并发下差距更大。

# 阶梯 1:HTTP 撑不起聊天,所以要 WebSocket

## 完整讲解

### 问题:服务器怎么"主动"告诉你有新消息?

HTTP 的规矩是**一问一答**:客户端发请求,服务器回响应,然后这事就结束了。
服务器**永远不能先开口**——它甚至不记得你是谁(所以才需要 cookie/token)。

可聊天软件的核心需求恰恰是:**A 发了消息,服务器要立刻主动塞给 B。** HTTP 天生干不了这个。

### 笨办法:轮询

让 B 的浏览器每秒问一次:"有我的新消息吗?"——"没有。""有我的新消息吗?"——"没有。"
- 99% 的请求都是白问,每次还带全套 HTTP 头(几百字节),百万用户每秒百万次白问,服务器被问死
- 消息平均延迟 = 轮询间隔的一半,做不到"即时"

(改良版叫**长轮询**:服务器收到"有吗"先不回答,攥着这个请求直到真有消息才回——好一点,但每收一条消息都要重新发一次请求,本质还是别扭。)

### 正解:WebSocket——电话线不挂断

WebSocket 的思路简单粗暴:**第一次还是用 HTTP 敲门,敲开后双方约定"这条 TCP 线我们不挂了",
从此变成双向通道,谁有话谁直接说**,不再有"请求/响应"的概念,发的每段话叫一个**帧(frame)**。

敲门那一下叫**协议升级**:浏览器发一个带 `Upgrade: websocket` 头的 HTTP 请求,
服务器回 `101 Switching Protocols`,从此这条线改说 WebSocket 话。

### 心跳:怎么知道对面还活着?

电话线不挂断带来新问题:对方手机没电了(浏览器崩了、网断了),你这头**可能毫无感觉**,
还攥着一条死线——内存白占,消息推过去石沉大海。

解法是**心跳**:服务器定期发 `ping` 帧,客户端必须回 `pong`。约定好"超过 N 秒没听到 pong 就当你死了",
服务器主动挂线、清理资源。

### 对应到你的代码

- `internal/gateway/handler/router.go:103`——WebSocket 入口是 `GET /api/v1/ws`,注意它**先过 `middleware.AuthRequired()`(JWT 鉴权)再升级协议**:先验明正身,再交出长连接
- `router.go:130` 附近——`SetPongHandler`,就是上面说的心跳应答处理
- `internal/gateway/hub/hub.go`——连接花名册:一个 `map[userID]*websocket.Conn` 加读写锁。
  Register=登记,Unregister=注销,Push=按花名册找到某人的电话线、把消息写进去

## 实验(15 分钟)

1. `cd deploy && docker compose up -d`(已 build 过,秒起)
2. 浏览器开**两个窗口**(其中一个用无痕模式)访问 `http://localhost:5173`,注册两个账号并登录
3. 两个窗口都按 F12 → Network → 筛选 **WS** → 点开那条 `/api/v1/ws` 连接
4. 看三样东西:
   - **Headers 标签**:请求头里的 `Upgrade: websocket`、响应状态 `101 Switching Protocols`——亲眼看到"协议升级"
   - **Messages 标签**:窗口 A 给 B 发消息,盯着 B 的 Messages——**B 没有发出任何请求,帧自己到了**。这就是"服务器主动推送",HTTP 做不到的那件事
   - 等一会儿,看有没有周期性的 ping/pong 帧(心跳)

## 自查题

1. 轮询和 WebSocket 长连接,各自的代价是什么?(各答两条)
2. 网关怎么发现"用户已经断线"?对应代码里的什么机制?
3. 为什么 `/api/v1/ws` 路由要先过 JWT 中间件再升级协议?不验直接升级会怎样?

## 参考答案(先自己答!)

1. 轮询的代价:① 海量无效请求,每次带全套 HTTP 开销,服务器扛请求风暴;② 消息延迟 = 间隔的一半,实时性差。长连接的代价:① 服务器要为每条连接维护内存(goroutine + 缓冲区),百万连接就是百万份,这就是"海量连接管理"难题;② 需要心跳、断线重连等额外机制,状态变复杂(HTTP 无状态反而省心)。
2. 两条路:① 读这条连接报错(对方正常关闭或 TCP 断开);② 心跳超时——服务器发 ping,超过设定时间没收到 pong(`SetPongHandler` 配合读超时),判定死线,调用 `hub.Unregister` 清理。
3. 长连接是昂贵资源,不验身份就升级,任何人都能白嫖连接(占内存、收别人消息)。先过 `AuthRequired` 确认 JWT 有效、知道这条线属于哪个 userID,才能在 hub 里登记 `userID → conn` 的映射——后面"推消息给某人"全靠这个映射。

# 阶梯 2:为什么要 Kafka(全项目最重要的一级)

## 完整讲解

### 问题:同步写库,高峰期会发生什么?

设想没有 Kafka 的版本:网关收到消息 → 直接写 MySQL → 写完才回复用户"发送成功"。

- 写一次 MySQL 约 5–10ms,一个实例一秒最多扛一千多次同步写
- 晚高峰来了 5000 条/秒:数据库排队 → 每个网关 goroutine 都卡在"等写库"这步(回想阶梯 0:同步=干等)→
  卡住的 goroutine 越堆越多 → 内存暴涨、新用户握手没人理 → **整个入口瘫痪**
- 更糟的是连坐:数据库一打嗝,用户连"发消息"按钮都按不动了——明明只是存储慢,却把接待也拖死了

### 解法:中间放一个"留言箱"

食堂打饭窗口为什么不堵?因为点单和做菜分开:前台只管收单子贴墙上,后厨按自己节奏撕单子炒菜。

把这个思路搬过来:**网关收到消息,只往"留言箱"里一扔(不到 1ms),立刻回头接待下一个;
另一个程序(message 服务)从留言箱按自己的节奏取出来,做权限校验、生成 ID、写库。**

这个留言箱就是**消息队列**,Kafka 是一个工业级实现:留言**先写到磁盘上**(取信人崩溃了信还在),
能扛每秒几十万条,还能让多个取信人分工合作。

### 这就解释了你背过的两个黑话

- **削峰填谷**:高峰期 5000 条/秒涌进来,Kafka 先全装下(峰被削平);message 服务始终按它能消化的
  1000 条/秒稳定取(谷被填上)。流量像洪水,Kafka 是水库。
- **解耦**:扔信的人(gateway)和取信的人(message)互不认识、互不等待。message 服务崩了、升级了、
  重启了,gateway 毫无感觉,照常收消息——你做实验时会亲眼看到这一幕。

### 必须知道的 Kafka 词汇(只这五个)

| 词 | 大白话 |
|---|---|
| topic | 哪一类留言箱(本项目:进箱 `chat.msg.incoming`,出箱广播一个 topic) |
| producer | 往箱里扔信的(gateway) |
| consumer | 从箱里取信的(message 服务、agent 服务) |
| offset | 书签:"我取到第几封了"。崩溃重启后从书签处继续,这就是消息不丢的关键 |
| 落盘 | 信写在磁盘上不是只在内存里,Kafka 自己崩了重启,信还在 |

### 代价也要诚实地知道

异步不是白来的:用户点发送,看到的是"已发出"而不是"已落库"——存储是**稍后才完成**的(术语叫最终一致)。
要是 message 服务挂一小时,消息会迟到一小时(但不丢)。面试时能主动说出代价,是高分项。

### 对应到你的代码

- `internal/gateway/producer/producer.go`——网关往 Kafka 扔消息
- `internal/message/service/service.go`——消费、校验(gRPC 问 user 服务)、雪花 ID、落库、再投回广播 topic
- `pkg/kafka/kafka.go`——读写 Kafka 的封装;`pkg/model/kafka.go`——信封格式

## 实验(20 分钟,本讲义最重要的实验)

```bash

```
网页上用 A 给 B 连发 5 条消息。观察:**发送不报错**(信进了箱子),但 B 收不到、刷新也没有(没人取信)。

## 自查题

1. 没有 Kafka、网关直接同步写库,1000 并发时具体卡死链条是什么?(从 goroutine 说起,一环环说)
2. 消息什么情况下会丢?(提示:扔信端和取信端各有一种丢法)
3. 项目里哪些环节走 Kafka、哪些不走?为什么发消息走 Kafka,登录却不走?

## 参考答案(先自己答!)

1. 每个连接的 goroutine 同步等写库(10ms)→ 高峰期数据库排队,等待时间变成 100ms、1s → goroutine 全部卡住不释放 → 数量和内存暴涨 → 新连接握手无人处理 → 用户端表现为"连不上、发不出",入口整体瘫痪。根因:把慢操作(写库)放在了接待的主路上。
2. 扔信端:producer 扔出去不等 Kafka 确认(ack)就当成功,网络抖动这封信就没了。取信端:consumer 先挪书签(提交 offset)再处理,处理到一半崩溃——重启后从新书签继续,崩溃前那封信永远跳过了。(正确姿势:先处理完再挪书签,代价是崩溃后可能重复处理同一封信,所以要"至少一次 + 处理端去重",往深处挖就是面试高频的"消息语义"。)
3. 消息收发走 Kafka(量大、可以稍后完成);登录/好友校验走 gRPC 同步调用(必须**立刻**知道结果——不能"稍后告诉你密码对不对")。判断标准:这件事能不能接受"稍后完成"。能 → 队列;不能 → 同步调用。

# 阶梯 3:Redis 在干嘛——一块大家共用的内存

## 完整讲解

### 问题:每条消息都要查"对方在不在线、连在哪台网关"

message 服务处理完一条消息,要推给 B,先回答两个问题:B 在线吗?B 的 WebSocket 连在**哪台**网关上?
(将来网关不止一台,消息必须送到 B 实际连着的那台。)

去 MySQL 查?两个毛病:① 阶梯 0 的表——磁盘级耗时,每条消息都查一次,高峰期数据库先死;
② 在线状态是秒级变化的**临时数据**(上线写、下线删),拿持久化数据库存它,杀鸡用牛刀还把牛累死。

### 为什么不放进程自己的内存?

放 gateway 进程的 map 里,一台网关时确实可以。但两台网关呢?A 连在网关 1,B 连在网关 2,
**网关 2 的内存里根本没有 A 的影子**——各进程的内存互相看不见。而且进程一重启,全丢。

### 解法:Redis = 所有服务共用的、带过期时间的大字典

Redis 就是一个独立进程,数据全放内存(单次操作 ~0.1ms),所有服务都能连它读写。
三个特性正好对症:
- **快**:内存级,扛十万级 QPS 不费力
- **共享**:网关 1 写的"A 在线,连在我这",message 服务和网关 2 都看得见
- **会过期(TTL)**:给键设个寿命,到点自动删——这是处理"脏数据"的灵魂,见自查题 2

本项目还让 Redis 兼第二个职:**热消息缓存**——每个会话最新 100 条存成 Redis List,
打开聊天窗时直接从内存拿(快),往前翻历史才去 MySQL(慢但少见)。又是阶梯 0 那把钥匙:常用的放快处。

### 对应到你的代码

- `pkg/redisclient/client.go`——连接封装
- 在线状态:gateway 连接建立/断开时写/删;message 服务推送前读
- compose 里 `REDIS_ADDR: "redis:6379"`

## 实验(15 分钟)

```

```

## 自查题

1. 在线状态为什么不放 MySQL?为什么不放网关自己的内存?(两个"为什么不"各答两条)
2. 网关进程崩溃,没来得及 DEL,Redis 里残留"B 在线"的脏数据——后果是什么?标准解法是什么?
3. 聊天记录明明在 MySQL 里,为什么还要在 Redis 存最新 100 条?什么时候这份缓存和 MySQL 会不一致?

## 参考答案(先自己答!)

1. 不放 MySQL:① 磁盘级耗时,每条消息查一次扛不住;② 秒级变化的临时数据不值得持久化,写放大严重。不放进程内存:① 多台网关互相看不见,跨网关路由就断了;② 进程重启全丢,且 message 服务(另一个进程)无法读取。
2. 后果:message 服务以为 B 在线,把消息推给一台早没这条连接的网关,推送失败或消息黑洞。标准解法:**TTL + 心跳续期**——写在线状态时设 60 秒过期,网关每 30 秒(随心跳)续一次;进程崩了没人续,60 秒后键自动蒸发,脏数据自愈。这个"租约"思想在分布式系统里到处都是,面试爱问。
3. 因为"打开聊天窗看最近消息"是最高频操作,直接读内存把 MySQL 解放出来。不一致窗口:消息已落库但还没写进缓存的瞬间,或缓存写失败时——所以缓存只当加速器,MySQL 才是真相之源(翻旧页时回源查库)。

# 阶梯 4:雪花算法——怎么造一个不会撞车的 ID

## 完整讲解

### 问题:每条消息需要一个"全局唯一、大致有序"的编号

为什么需要:去重(同一条消息别存两遍)、排序(聊天记录按先后排)、翻页(从某条往前取 50 条)。

**方案一:数据库自增 ID?** 一台 MySQL 时没问题。但 message 服务开两个实例、或将来消息表拆成多张(分库分表),
各自数 1、2、3 必然撞车;让数据库统一发号 = 每条消息多一次数据库往返,发号器本身成了瓶颈和单点。

**方案二:UUID?** 128 位随机数,确实不撞。但它**完全无序**:MySQL 的 InnoDB 主键是按大小顺序组织的
B+ 树(想象图书馆书架按编号排书),随机编号的新书每次都要插进书架中间——把后面的书全挪一遍(页分裂),
插入性能稀烂;而且 128 位太长,索引又大又慢。

**方案三:雪花(Snowflake)——自己拼一个 64 位整数:**

```
| 1位符号 | 41位:毫秒时间戳 | 10位:机器编号 | 12位:毫秒内序号 |
```

- 41 位毫秒 ≈ 能用 69 年
- 10 位机器号 = 最多 1024 台机器各自独立发号,**不用商量、绝不撞车**(每台机器的 NODE_ID 不同——看 compose 里每个服务的 `NODE_ID` 环境变量)
- 12 位序号 = 同一台机器同一毫秒内能发 2^12 = **4096** 个
- 高位是时间戳 → ID 天然**大致按时间递增**,对 B+ 树是顺序追加,插入快

不用网络、不用协调、一把锁本地生成,一举全收。

### 时钟回拨:这个算法唯一的命门

机器的系统时间不是绝对可靠的——NTP 校时可能把时钟**往回调**几毫秒。
回拨后,"同一毫秒"会重演一遍,序号重数,**可能发出和过去重复的 ID**——主键冲突,消息互相覆盖,灾难。

看你的 `pkg/snowflake/snowflake.go`(写得不错,这就是面试加分点):
- 回拨 ≤ 5ms:原地 `sleep` 等时钟追上来(代价:这几毫秒不发号,可接受)
- 回拨 > 5ms:直接 **panic** 拒绝服务

为什么宁可崩?因为"发重复 ID"是数据正确性事故(静默腐烂,事后难查),
"停止发号"只是可用性事故(立刻报警,人来处理)。**宁可死得响亮,不可错得安静**——这个取舍本身就是面试题。
(替代方案:① 一直等到追平——回拨大时服务长时间卡死;② 返回错误让调用方重试——把复杂度扔给了每个调用者。)

## 实验(20 分钟,这级要写代码——自己敲,这正是你在练的)

在项目里建 `cmd/idgen-demo/main.go`,约 20 行:设置 `NODE_ID` 环境变量,调 `snowflake.NewFromEnv()`,
循环打印 10 个 `NextID()`。然后**手动拆位**验证(提示,对照源码常量):

```go
id := gen.NextID()
fmt.Println("时间戳部分:", id>>22)          // 右移 10+12 位
fmt.Println("机器号部分:", (id>>12)&1023)   // 应该等于你设的 NODE_ID
fmt.Println("序号部分:  ", id&4095)
```

跑两次:循环里不加 sleep(看同一毫秒内序号 0,1,2,…递增)、加 `time.Sleep(time.Millisecond)`(看序号归零、时间戳走动)。

## 自查题

1. 数据库自增和 UUID 各自为什么被否?(每个两条)
2. 同一毫秒发第 4097 个 ID 时,代码会发生什么?(去源码里找答案)
3. 回拨处理的三种方案(等待/报错/panic)各自的代价?你的项目选了哪种组合,为什么?

## 参考答案(先自己答!)

1. 自增:① 多实例/分库分表会撞;② 中心发号则多一次网络往返且是单点。UUID:① 无序导致 B+ 树页分裂,插入性能差;② 128 位太大,索引臃肿。(加分:UUID 还暴露不了时间信息,而雪花 ID 能反解出生成时间,排查问题好用。)
2. 序号 `(sequence+1) & 4095` 归零,代码进入自旋:循环读当前时间直到进入下一毫秒才发号——也就是"这一毫秒的 4096 个名额用完了,原地等下一毫秒"。
3. 一直等待:回拨大时服务卡死无响应;返回错误:每个调用方都要写重试逻辑,复杂度扩散;panic:服务崩溃但绝不发错号,靠重启和告警兜底。本项目组合:小回拨(≤5ms)等待——代价微小不值得崩;大回拨 panic——正确性优先于可用性。

# 阶梯 5:gRPC——让"问别的服务一个问题"像调用本地函数

## 完整讲解

### 问题:message 服务要问 user 服务"这俩人是好友吗"

消息落库前要校验权限,但好友关系归 user 服务管(微服务各管各的数据)。这是一次**跨进程的函数调用**:
我这边想写 `IsFriend(a, b)`,实际执行却在另一个进程里。

**朴素方案:HTTP + JSON。** 能用,但:① JSON 是文本,序列化/解析慢、体积大;
② 没有类型约束——对方把字段从 `user_id` 改成 `uid`,你编译期毫无察觉,运行时才炸。

**gRPC 的方案:先签合同,再生成代码。**
1. 用 `.proto` 文件把接口写成合同(看 `api/user/`、`api/message/` 目录):有哪些方法、参数什么类型、返回什么
2. 代码生成器按合同给**两边**生成强类型代码——调用方拿到一个长得像本地函数的 stub,服务方拿到一个待实现的接口
3. 传输用 **protobuf 二进制**(比 JSON 小好几倍、编解码快一个量级),跑在 HTTP/2 上(一条连接并发跑多个请求)

效果:`resp, err := userClient.CheckFriend(ctx, req)` ——看起来是本地调用,实际跨了进程。
字段改了?重新生成代码,**编译期就报错**。这就是"强类型合同"的价值。

### 最重要的一课:gRPC 和 Kafka 的分工(同步 vs 异步)

| | gRPC | Kafka |
|---|---|---|
| 比喻 | **打电话**:必须立刻得到答复,对方不接=失败 | **发微信**:扔出去就走,对方慢慢看 |
| 时序 | 同步,调用方等结果 | 异步,扔完就回头干活 |
| 对方挂了 | 我立刻报错(实验里你会亲眼看到) | 我毫无感觉,消息排队等它复活 |
| 本项目用在 | 好友校验、用户信息——**必须立刻知道答案**的事 | 消息流转——**可以稍后完成**的事 |

一个系统里两者并存、各司其职,选错才是事故:权限校验走 Kafka?校验结果还没回来消息就落库了。
消息落库走 gRPC 同步?回到阶梯 2 的雪崩。**判断标准一句话:这个调用能不能接受"稍后才完成"。**

### 对应到你的代码

- `api/user/`、`api/message/`——proto 合同和生成的代码
- `internal/gateway/client/user_client.go`、`message_client.go`——调用方的 stub 封装
- `internal/message/service/service.go`——消费 Kafka 消息后,gRPC 调 user 服务校验,体现两者协作

## 实验(10 分钟)

```bash
docker compose stop user        # 杀掉被调用方
docker compose logs -f message  # 盯着调用方日志
```
网页上发一条消息。看 message 服务报出的 gRPC 连接错误——**同步调用,对方死=我立刻失败**。
对比阶梯 2:stop message 时 gateway 一点事没有(异步,Kafka 兜着)。两次实验放一起,同步/异步的差别就长在你脑子里了。
```bash
docker compose start user       # 记得复活
```

## 自查题

1. gRPC 相比 HTTP+JSON 的两大优势是什么?各自的原理?
2. 本项目里把"好友校验"从 gRPC 改成走 Kafka,会出什么事故?反过来,消息落库改成 gRPC 同步调用呢?
3. user 服务挂了,gateway 和 message 谁先受伤、表现是什么?(结合两次实验回答)

## 参考答案(先自己答!)

1. ① 性能:protobuf 二进制比 JSON 文本小且编解码快,底层 HTTP/2 一条连接并发复用;② 强类型合同:proto 文件生成两端代码,接口改动在编译期暴露,而不是运行时炸。
2. 校验改 Kafka:校验是异步的,结果回来之前消息已经往下走了——要么先落库后发现无权限(脏数据),要么所有消息都得挂起等回执(自己发明了一个蹩脚的同步)。落库改同步 gRPC:网关重新被慢操作拖住,阶梯 2 的雪崩回来了。
3. 都受伤但方式不同:gateway 在登录/鉴权时同步调 user,立刻报错,用户登录失败;message 消费到需要校验的消息时调用失败——取决于实现,要么这条消息处理失败重试,要么丢弃。同步依赖 = 故障立刻传染,这就是为什么"能异步的尽量异步"。

# NexusChat 面试手册(教科书版)

## 第〇章 使用说明(先读,直接决定你能不能用好这本手册)

### 0.1 这本手册和其他文档的关系

- **`学习阶梯.md`** 负责让你**真懂**(实验 + 从零讲解)——每章开头标了对应阶梯,没走完对应阶梯别背本章
- **本手册**负责把"懂"翻译成**面试语言**:怎么组织、怎么应对追问、哪里有坑
- 顺序铁律:**先阶梯,后手册**。跳过阶梯直接背,就回到了"只会背不理解"的老路

### 0.2 三段式答题法(所有题通用的模板)

1. **一句话结论**(先给答案,别绕)
2. **原理 + 数字**(为什么,带量级:写库 ~10ms、Redis ~0.1ms、雪花每毫秒 4096 个)
3. **落到我的项目**("在 NexusChat 里,我是这么做的/我遇到的情况是…")

第三段是你和背书型候选人拉开差距的地方——面试官每天听一百遍标准答案,只有"你的项目里的真实细节"是新鲜的。

### 0.3 实现状态标记(本手册的诚实系统)

- ✅ **已实现**:代码里真有,放心讲,准备好被追问细节
- 🔧 **待实现**:你已知道方案、正在做(如 Agent Worker、writePump 重构)——讲的时候说"我正在做/我修复中",**做完之前不许说成"我做了"**
- 📋 **仅方案**:项目没做,但你必须会讲方案——标准话术:"项目里没做这个,但我考虑过,方案是…"

**为什么这套标记对你生死攸关**:面试挂掉的最快方式,不是"不知道",而是**声称做过却答不上细节**。前者扣一分,后者整场作废。

### 0.4 追问的本质

面试官的策略就一条:**沿着 why 链往下挖,直到你说"不知道"**——他要测的是你的"理解深度到哪一层"。
所以:① 每题后面的「追问链」要练到至少接住前两层;② 到达边界时,标准止损话术:
**"这块我只了解到 X 层,再深的 Y 我目前说不准,不想猜——但我的理解方向是…"**(诚实 + 给出方向 = 比硬编强十倍)

# 第一章 开场必备(出现概率 100%,必须烂熟)

## 1.1 六十秒版本(自我介绍后的第一问:"介绍下你的项目")

> "NexusChat 是我做的一个分布式实时聊天系统,Go 写的,拆了四个微服务:网关管 WebSocket 长连接,用户服务管账号和好友关系,消息服务管落库和分发,还有一个 AI Agent 服务接入了我自己用 Python 写的智能体系统,让聊天室里有一个带长期记忆的 AI 成员。
> 技术上的核心思路是**异步化**:网关收到消息只往 Kafka 一扔就立刻响应,验权、生成雪花 ID、写 MySQL、推送,全部在后端异步完成——所以入口的响应速度和数据库压力是解耦的。服务间同步调用走 gRPC,在线状态和热消息放 Redis。
> 这个项目我最大的收获是把'为什么要消息队列、为什么要缓存'这些概念,从背概念变成了亲手验证——我可以详细讲任何一块。"

(最后一句是钩子,把面试官往你准备最充分的地方引。)

## 1.2 三分钟版本(白板/口述架构)

按**一条消息的旅程**讲,比按"我有哪些服务"讲生动十倍:

> "用户 A 给 B 发一条消息,完整旅程是这样的:
> ① A 的消息通过 WebSocket 帧到达**网关**——这条连接是登录后建立的,握手前先过 JWT 鉴权;
> ② 网关不做任何重活,把消息投进 Kafka 的 incoming topic,立刻给 A 回'已发出'——这是整个架构的关键决策,网关永远不等数据库;
> ③ **消息服务**消费这条消息:先 gRPC 调用用户服务验证'A 和 B 是不是好友'——这一步必须同步,因为要立刻知道答案;然后用雪花算法生成全局唯一且趋势递增的消息 ID,写 MySQL,同时把最新消息缓存进 Redis 的 List;
> ④ 处理完投到 outgoing topic,网关消费到之后查 Redis 在线状态——B 在线、连在哪台网关——找到对应连接把消息推给 B;
> ⑤ 如果消息 @ 了 AI,**Agent 服务**也会消费到它,调用我的 Python 智能体(带分层记忆)生成回复,再把回复当成一条普通消息投回 incoming,走一遍同样的旅程。
> 同步和异步的分工原则就一句话:**必须立刻知道答案的走 gRPC,可以稍后完成的走 Kafka**。"

## 1.3 "项目是 AI 辅助开发的吗?"(2026 年必考,你的生死题)

**标准答法(背熟,一字一句):**

> "是的,我大量使用了 AI 辅助开发,这是我刻意练习的工作方式。架构设计、技术选型、每个组件为什么这么选,是我的决策;具体编码 AI 参与很多。但我对代码库做了完整的审计——比如我在审计网关代码时,发现连接管理 hub 的推送路径在读锁下直接对 websocket.Conn 并发写,而 gorilla/websocket 明确不支持并发写,这是一个真实的 data race 隐患,我正在按'每连接专属写 goroutine + channel'的标准模式重构它。我的观点是:AI 时代工程师的核心价值不是逐行手敲,而是架构判断和质量把关——但前提是基础功扎实到能给 AI 挑错,这正是我花最多时间练的。"

**为什么这是最优答法**:① 不撒谎(撒谎会在追问下崩);② 把弱点翻转成"会审计 AI 代码"的稀缺能力;③ 那个 bug 故事是真的、可验证、有技术深度。
**前提**:你必须真的把 hub 重构完(见 3.4),否则这段话就是空头支票。

## 1.4 "项目的最大难点/挑战是什么?"

准备两个,按面试方向选用:

- **偏工程**:讲 hub 并发写 bug 的发现与修复(完整 STAR:审计时读 gorilla 文档发现写不是并发安全的 → 复现思路(心跳和推送两个 goroutine 同时写)→ 标准修复模式 → 学到"库的并发契约必须读文档,不能想当然")
- **偏架构**:讲"同步 vs 异步的边界划分"(为什么验权必须 gRPC 同步、落库必须 Kafka 异步,选错各会发生什么——见 8.3)

## 1.5 "为什么做这个项目?"

> "两个目的:一是把分布式后端的核心组件——长连接、消息队列、缓存、RPC——放进同一个真实场景里串起来理解,单独学每个组件很难体会它们为什么被组合;二是我对 AI 应用方向感兴趣,之前用 Python 写过一个带分层记忆的智能体系统,想验证把它作为独立服务接入实时聊天的完整链路。"

# 第二章 全局架构(对应阶梯 0,出现率 ★★★★★)

## 2.1 为什么拆微服务?单体不行吗? ✅

**🎯 考点**:你是真理解拆分的代价与收益,还是为了简历好看而拆。

**🗣️ 人话**:单体 = 所有功能在一个程序里,部署简单但一荣俱荣一损俱损;微服务 = 拆成多个独立程序,各自部署扩容,代价是引入网络调用和复杂度。

**📝 面试版**:
> "对这个规模,单体完全可行,我拆微服务是刻意的,理由有三:
> ① **扩容曲线不同**——网关的瓶颈是连接数(内存),消息服务的瓶颈是写库 QPS(CPU/IO),拆开才能各自独立加机器;
> ② **故障隔离**——AI 调用动辄秒级,Agent 服务卡死不能影响正常聊天,所以它必须是独立进程,通过 Kafka 隔离;
> ③ 坦率说也有**学习目的**——我想在真实场景里掌握 gRPC 和 Kafka 的工程用法。
> 微服务的代价我也踩到了:本地调试要起 8 个容器、服务间调用要处理超时和部分失败,这些在单体里都不存在。"

**⚠️ 追问链**:
- "拆分的边界怎么定的?" → 按**数据的所有权**:用户/好友数据归 user,消息数据归 message,谁拥有数据谁提供接口,其他服务不许直连别人的库
- "服务发现怎么做的?" → 📋 诚实:"目前是 compose 网络里的固定地址,生产环境该用注册中心(etcd/Consul),原理是服务启动时注册自己、调用方订阅地址变化"
- "分布式事务?" → 见 12.4

**💣 坑**:吹"为了高可用/支撑大流量而拆"——面试官一句"你压测过吗"就把你钉死。承认学习目的反而加分。

## 2.2 消息流转完整链路 ✅(必考,1.2 的三分钟版就是答案)

追加一个数字版速记:**网关收到消息 → 回包 < 1ms(只投 Kafka);全链路落库+推送 ~ 几十 ms(异步,用户无感)**。

**⚠️ 追问链**:
- "为什么网关回的是'已发出'不是'已送达'?" → 因为落库和推送是异步的,此刻还没发生;客户端要的是即时反馈,最终状态靠后续推送确认(微信也是这个设计:转圈→对勾)
- "B 不在线怎么办?" → 消息已落库;B 上线后拉历史(Redis 最新 100 条 + MySQL 翻页)。📋 "离线推送(APNs 等)是没做的,方案是离线时转投推送服务"

# 第三章 WebSocket 与连接管理(对应阶梯 1,出现率 ★★★★★)

## 3.1 为什么用 WebSocket?和轮询/长轮询区别? ✅

**🗣️ 人话**:HTTP 只能客户端先开口,聊天需要服务器主动推。轮询 = 每秒问"有新消息吗",99% 白问;长轮询 = 服务器攥着请求等有消息才回,好一点但每条消息都要重新发请求;WebSocket = 握手后这条 TCP 线不挂了,双方随时互发,真正的双向通道。

**📝 面试版**:
> "聊天的核心需求是服务端主动推送,HTTP 的请求-响应模型天然不支持。轮询的问题是无效请求风暴 + 平均延迟等于半个轮询间隔;长轮询减少了空响应但每条消息都有重建请求的开销。WebSocket 通过一次 HTTP Upgrade 握手(101 Switching Protocols)把连接升级成全双工帧协议,之后服务端可以零延迟推送,每条连接的常驻成本就是一个文件描述符加 goroutine。我项目里入口是 `GET /api/v1/ws`,特意放在 JWT 中间件后面——先验明身份,再交出长连接这个昂贵资源,同时网关也由此知道这条连接属于哪个 userID,后续推送全靠这个映射。"

**⚠️ 追问链**:
- "握手细节?" → 请求带 `Upgrade: websocket` + `Sec-WebSocket-Key`,服务端回 101 和 `Sec-WebSocket-Accept`(对 Key 做固定算法运算,证明服务端真懂 WS 协议而不是误转发)
- "为什么不用 SSE?" → SSE 只有服务端→客户端单向,且本质还是 HTTP;聊天要双向
- "HTTP/2 的 server push 呢?" → 推的是静态资源不是应用消息,且已被弃用;答出这个是亮点

## 3.2 心跳机制 ✅(代码:`router.go` 的 `SetPongHandler`)

**🗣️ 人话**:线不挂断,就得定期喊"还在吗"——不喊,对面悄悄死了你还攥着死线:内存白占、消息推进黑洞。

**📝 面试版**:
> "服务端每 30 秒发一个 Ping 帧,同时把读超时设到 90 秒;客户端回 Pong 时,PongHandler 里把读超时往后推 90 秒。只要 90 秒内没有任何数据(包括 Pong),读操作超时报错,连接判死,走清理流程。心跳还有第二个职责:**顺带给 Redis 的在线状态续 TTL**——这两个超时机制是配套的,连接活着,在线状态就一直续;进程崩了,两边都会自动过期。"

**⚠️ 追问**:"为什么读超时是心跳间隔的 3 倍?" → 容忍偶发丢一两个 Pong(网络抖动),避免误杀;1 倍会疯狂误杀,10 倍则死线发现太慢。工程上 2–3 倍是惯例。

## 3.3 海量连接怎么管理? ✅(代码:`hub.go`)

**📝 面试版**:
> "Go 在这里优势明显:每条连接一个 goroutine,初始栈才几 KB,runtime 做 M:N 调度,几万连接跑在十几个 OS 线程上。我的 ConnHub 用 `map[userID]*conn` 加 `sync.RWMutex`:推送是读多(RLock 可并发),注册注销是写少(Lock 互斥)。进一步优化方向是分片锁——把 map 按 userID 哈希拆成 N 个分片各自带锁,锁竞争降 N 倍。"

**⚠️ 追问链**:"百万连接的瓶颈在哪?" → 依次是:内存(每连接的 goroutine 栈+读写缓冲,约几十 KB,百万连接几十 GB → 要多网关分摊)、文件描述符上限(ulimit 调优)、心跳风暴(百万连接每 30s 一个 ping 本身就是 3.3 万 QPS)。能按这个顺序说,就是亮点。

## 3.4 并发写问题(你的黄金故事)🔧 → 重构完成后改 ✅

**🗣️ 人话**:gorilla/websocket 的文档明确说:**同一连接,同时只能有一个 goroutine 在写**。而当前 hub 的 `Push` 在读锁下直接 `WriteMessage`——读锁允许多个 goroutine 同时进来,两个人同时给同一个用户推消息(或心跳 goroutine 和推送撞上),就是 data race,轻则帧错乱重则 panic。

**📝 面试版(重构完成后)**:
> "我审计 AI 生成的网关代码时发现一个并发隐患:推送路径在 RLock 下直接写 conn,但 gorilla/websocket 的写不是并发安全的——RLock 恰恰允许多个推送 goroutine 并行进入。我按官方 chat example 的标准模式重构:每个连接配一个专属 writePump goroutine 和一个带缓冲的 send channel,所有写入(推送、心跳、关闭帧)都只往 channel 投递,writePump 是唯一写者,从结构上消灭了并发写。顺带解决了**背压**问题:channel 满说明客户端消费太慢,直接断开——防止一个慢客户端把内存拖爆。"

**⚠️ 追问链**:
- "为什么读锁防不住?" → 读锁防的是"读 map 和写 map 互斥",防不住"两个读到同一个 conn 的人同时用它"——锁保护的是 map,不是 conn
- "channel 满了阻塞还是丢弃?" → 用 `select + default`:满了走 default 断开连接。阻塞会把推送方拖死,等于把慢客户端的问题传染给全系统
- "怎么发现这类问题?" → go 自带 `-race` 检测器跑测试;读第三方库的并发契约文档

**💣 坑**:在重构完成前就把这段说成"我做了"。面试官让你打开代码,完蛋。

## 3.5 断线重连与消息不丢 📋(没实现,会讲方案即可)

> "项目没实现,方案是:客户端记住收到的最后一条消息 ID(雪花 ID 趋势递增,天然是游标),重连后带着这个 ID 拉增量(`WHERE conversation_id=? AND id>?`),服务端消息已全部落库所以不存在丢——断线丢的只是'推送',不是'数据'。"

# 第四章 Kafka 与异步架构(对应阶梯 2,出现率 ★★★★★)

## 4.1 为什么要 Kafka?✅(全项目第一考点)

**🗣️ 人话**:回到阶梯 2 的画面——网关直接写库,高峰期所有 goroutine 卡在等数据库,入口瘫痪。中间放个"留言箱",网关扔了就走(<1ms),消息服务按自己节奏取。**削峰填谷** = 洪峰先装水库;**解耦** = 扔信的和取信的互不认识,一边挂了另一边照常。

**📝 面试版**:
> "核心动机是把慢操作挪出接入主路。写一次 MySQL 约 5–10ms,同步模式下高峰期网关的 goroutine 会全部阻塞在等库上,连接堆积、新握手超时,存储慢拖死接待。引入 Kafka 后网关只做'收 + 投递',毫秒级响应;消息服务按自己的消费能力稳定处理,流量峰值由 Kafka 落盘缓冲。我做过一个验证:把消息服务整个 stop 掉,网关照常收消息毫无感知,消息在 Kafka 排队;服务恢复后积压消息全部补处理,一条不丢——这就是解耦和削峰的直观证明。"

(最后这句来自你亲手做过的阶梯 2 实验——**亲手做过的实验是你最硬的面试素材**。)

**⚠️ 追问链**:
- "代价呢?" → 最终一致:用户看到"已发出"时其实还没落库;链路变长,排查问题要跨服务追踪。主动说代价 = 高分
- "为什么不用 Redis 的 list/stream 当队列?" → Redis 是内存优先,持久化(RDB/AOF)不是为消息可靠性设计的;Kafka 落盘 + 消费位移 + 分区扩展,是专业干这个的。小流量用 Redis Stream 也行——能说出"也行,取舍是"比一边倒更显功力
- "和 RabbitMQ 比?" → RabbitMQ 是消息代理,路由灵活、单条消息确认;Kafka 是分布式日志,吞吐高、按位移顺序消费、适合流式场景。聊天消息是典型的日志型流,选 Kafka

## 4.2 消息会丢吗?三个环节逐一说 ✅/📋

**🗣️ 人话**:一封信从扔进箱到被处理完,三个环节各有一种丢法:扔的时候没确认就走、箱子还没写到磁盘就崩、取信人先挪书签再看信结果看到一半猝死。

**📝 面试版**:
> "分三段看:
> ① **生产端**:producer 配 `acks=all` 等所有副本确认 + 重试;`acks=0/1` 吞吐高但 Leader 崩溃窗口会丢——我的场景选可靠性。
> ② **Broker**:消息落盘,单机版我设 replication factor=1(本地环境),生产环境 3 副本。
> ③ **消费端**:关键是 offset 提交时机——**先处理完再提交**(我用手动提交,MySQL 写成功后才 CommitMessages)。反过来'先提交再处理',处理到一半崩溃,这条消息就永远跳过了。
> 先处理后提交的代价是崩溃后**重复消费**,所以必须配幂等——下一题。"

## 4.3 重复消费怎么办?(幂等)✅

> "消息体里带雪花 ID,MySQL 以它为主键——重复消费时第二次 INSERT 直接主键冲突,用 `INSERT IGNORE` 吞掉即可。这就是'至少一次投递 + 处理端幂等'的标准组合,业界共识是它的工程成本远低于追求'恰好一次'(那需要跨 Kafka 和 MySQL 的分布式事务)。"

**⚠️ 追问**:"哪些操作天然幂等,哪些不是?" → 设值类(set x=5)幂等;增量类(x+=1)不幂等,要靠唯一键去重或版本号。

## 4.4 消息顺序怎么保证? ✅

> "Kafka 只保证**单分区内**有序。投递时用 `conversation_id` 当 message key,同一会话哈希到同一分区,会话内自然有序——不同会话之间无序,但用户也感知不到。全局有序只能单分区,等于放弃并行,没必要。"

**⚠️ 追问**:"分区数怎么定?" → 上限看消费端并行度需求(分区数 = 最大并行消费者数),太多则文件句柄和重平衡开销大;经验值按目标吞吐/单分区吞吐估算,留 2 倍余量。

## 4.5 积压了怎么办? 📋

> "先看监控定位是消费慢还是生产突增。短期:加消费者实例(上限=分区数);中期:批量消费+批量写库;治本:扩分区。我的环境里 stop 消息服务再恢复,就是一次微型积压演练——恢复后消费速率就是它的自然消化能力。"

# 第五章 Redis(对应阶梯 3,出现率 ★★★★☆)

## 5.1 Redis 在项目里干嘛?为什么快? ✅

**🗣️ 人话**:两份活——"谁在线、连在哪台网关"的花名册 + 每个会话最新 100 条的快捷抽屉。快的原因:数据在内存(0.1ms vs 磁盘 10ms)、单线程无锁竞争、全程哈希表等 O(1) 结构。

**📝 面试版**:
> "两个用途:① 在线状态,`online:{user_id} → 网关地址`,带 TTL,解决'多网关时消息该路由到哪台'的问题;② 热消息缓存,Redis List 存每会话最新 100 条,打开聊天窗直接 LRANGE,不打 MySQL。
> 为什么快:内存操作、单线程事件循环避免锁和上下文切换、高效数据结构。注意单线程指命令执行,网络 IO 在 6.0 后是多线程的——说得出这个区分是加分项。"

## 5.2 在线状态:TTL + 心跳续期(租约思想)✅

> "写入时设 90 秒 TTL,心跳每 30 秒续一次。网关正常断开会主动 DEL;但如果网关**整个进程崩了**,来不及 DEL,这时 TTL 兜底——没人续期,90 秒后键自动蒸发,脏的'在线'状态自愈。这本质是**租约(lease)**:状态的有效性靠持续续约证明,而不是靠'记得清理'。分布式系统里到处是这个思想——服务注册的健康检查、分布式锁的过期时间,都是租约。"

(能把项目细节升华到"租约"这个通用概念,是从"做过"到"理解了"的标志,面试官眼睛会亮。)

## 5.3 缓存三件套:穿透/击穿/雪崩 📋(项目场景不典型,但必考必背)

**🗣️ 人话先分清**(背口诀:**穿透查不存在、击穿热键过期、雪崩集体过期**):
- **穿透**:查一个**根本不存在**的数据(恶意伪造 ID),缓存永远没有,每次都打穿到 MySQL → 解法:布隆过滤器拦住"一定不存在"的查询,或对空结果也缓存(短 TTL)
- **击穿**:一个**热点 key 过期瞬间**,上万并发同时涌向 MySQL → 解法:互斥锁(只放一个请求去回填,其他人等)或热点永不过期+后台刷新
- **雪崩**:**大批 key 同时过期**(比如都设了整点过期)→ 解法:TTL 加随机抖动,别让它们一起死

**📝 项目里怎么落**:
> "我的消息缓存场景天然防穿透:新消息是主动写入缓存(Write-Through 方向),不是读时回填,不存在'查不存在的 key';翻历史页直接走 MySQL 游标分页,不经过缓存。如果要做用户资料缓存,就要考虑三件套了——(然后背上面的解法)。"

## 5.4 缓存一致性 ✅

> "我用先写 MySQL、成功后再写 Redis。如果 Redis 写失败:库里数据是对的,缓存只是暂时旧/缺,下次读回填,最终一致——聊天场景可接受。反过来先写缓存再写库,库写失败缓存里就是一条'幽灵消息',严重得多。要更强一致就上'延迟双删'或订阅 binlog 更新缓存(Canal),聊天场景没必要。**原则:MySQL 是真相之源,缓存只是加速器。**"

# 第六章 雪花算法(对应阶梯 4,出现率 ★★★★☆,你的代码写得好,主动引导到这里)

## 6.1 为什么不用自增 ID / UUID? ✅

> "自增:多实例或分库分表会冲突,中心发号则是单点 + 每次多一跳网络;另外自增 ID 可预测,容易被遍历爬取。UUID:128 位太大、完全无序——InnoDB 主键是聚簇 B+ 树,随机插入造成频繁页分裂,写入性能差。雪花 64 位:41 位毫秒时间戳 + 10 位机器号 + 12 位序列——趋势递增对 B+ 树是顺序追加,每台机器独立发号无须协调,每毫秒单机 4096 个、可部署 1024 个节点。还能从 ID 反解出生成时间,排查问题很好用。"

## 6.2 时钟回拨(你的代码亮点,务必主动讲)✅

**🗣️ 人话**:NTP 校时可能把系统时间往回调几毫秒 → "同一毫秒"重演 → 可能发出重复 ID → 主键冲突、消息覆盖。

**📝 面试版**:
> "我的实现分级处理:回拨 ≤5ms,原地 sleep 等时钟追平——代价只是几毫秒不发号;回拨 >5ms,直接 panic 拒绝服务。为什么宁可崩?因为发重复 ID 是**正确性事故**——静默发生、污染数据、事后极难排查;停止发号只是**可用性事故**——立刻暴露、报警、重启解决。宁可死得响亮,不可错得安静。替代方案我也比较过:无限等待会让服务在大回拨时假死;返回错误则把重试复杂度扩散给每个调用方。"

**⚠️ 追问**:"同一毫秒第 4097 个请求?" → 序列号 `&4095` 归零后自旋等下一毫秒(代码里就是这么写的——`snowflake.go` 的 for 循环,你做阶梯 4 实验时验证过)。

# 第七章 MySQL 与数据设计(出现率 ★★★★☆,通用八股大头,项目只覆盖一部分)

## 7.1 表设计 ✅

> "三张核心表:users(账号)、conversations(会话,单聊/群聊统一抽象)、messages(消息,雪花 ID 主键,`(conversation_id, id)` 联合索引支撑按会话查询)。好友/群成员关系在 user 服务的库里——按数据所有权拆分。"

## 7.2 翻页为什么用游标不用 OFFSET? ✅

**🗣️ 人话**:`OFFSET 10000 LIMIT 20` 是"数到第 10000 行再给我 20 行"——数的那 10000 行白扫。游标是"从 ID=X 往前给我 20 条"——索引直接定位,深翻不变慢。

> "`WHERE conversation_id=? AND id<? ORDER BY id DESC LIMIT 20`,传上一页最后一条的 ID 当游标。雪花 ID 趋势递增,天然就是时间游标——这也是选雪花的隐藏好处。"

**⚠️ 追问**:"B+ 树为什么适合范围查询?" → 叶子节点是有序链表,定位起点后顺着链表扫即可。(更深的 B+ 树细节属于通用八股,用小林补,本手册不展开。)

## 7.3 分表 📋(没做,必须会讲)

> "单表过几千万行后考虑水平分表:按 `conversation_id` 哈希取模拆 16 张表,同一会话的消息保证在同一张表里,查询不跨表。代价:跨会话的全局查询要 scatter-gather(撒出去再聚合);扩容要数据迁移(一致性哈希可缓解)。我的项目量级用不上,但设计上雪花 ID + 按会话路由已经为它留好了路。"

# 第八章 gRPC 与微服务通信(对应阶梯 5,出现率 ★★★☆☆)

## 8.1 为什么 gRPC 不用 REST? ✅

> "两点:**性能**——protobuf 二进制比 JSON 小 3–10 倍、编解码快一个量级,HTTP/2 单连接多路复用;**契约**——proto 文件是强类型合同,两端代码自动生成,接口改动编译期就炸,而不是上线后才发现字段对不上。内部服务间高频小调用(每条消息都要验权),这两点都是刚需。对外的 HTTP API 依然是 REST——gRPC 是内部协议。"

## 8.2 超时与故障处理 ✅/📋

> "每个 gRPC 调用都带 `context.WithTimeout`(验权 500ms)——没有超时的同步调用等于把自己的命运交给对方。超时后这条消息处理失败,Kafka 不提交 offset,稍后重试。📋 重试风暴的防护(指数退避、熔断)项目里没做,方案是:连续失败超阈值就熔断,直接快速失败一段时间,给下游喘息——防止'下游越挂,上游越重试,下游更挂'的正反馈。"

## 8.3 同步 vs 异步的分工(架构题核心,1.2 已铺垫)✅

> "判断标准一句话:**这个调用能不能接受'稍后完成'**。好友校验不能——结果没回来消息就不能往下走,走 gRPC;落库推送能——用户已经拿到'已发出',走 Kafka。选错的后果:校验走异步 = 要么先落库再发现无权限(脏数据),要么挂起等回执(自己发明蹩脚的同步);落库走同步 = 网关重新被数据库拖死,异步化白做。"

# 第九章 JWT 鉴权(出现率 ★★★☆☆)

## 9.1 结构与验证 ✅

**🗣️ 人话**:JWT = 一张**自带防伪签名的门票**:票面写着你是谁、几点过期(Header+Payload,Base64 可直接读,**不是加密**!),签名是服务端用密钥对票面盖的章——改一个字,章就对不上。服务端验票只需重新盖章比对,**不用查库**,这就是"无状态"。

**⚠️ 追问链**:
- "Payload 能放密码吗?" → 绝不能,Base64 是编码不是加密,人人可读
- "和 Session 的区别?" → Session 状态在服务端(查库/查 Redis),JWT 状态在票里(无状态、好横向扩展);代价是 JWT 签出后**无法主动作废**
- "那怎么登出?" → 下一题

## 9.2 主动登出/吊销 📋

> "无状态的票收不回,只能引入一点状态:登出时把 token 标识(jti)写进 Redis 黑名单,TTL 设为 token 剩余寿命;每次验票多查一次黑名单(0.1ms,可接受)。或者短寿命 access token + refresh token 组合:access 15 分钟自然过期,吊销只需作废 refresh。"

|---|---|
